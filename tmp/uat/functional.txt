1.1 Purpose 
The purpose of this document is to detail the functional and non-functional requirements for the custom 
Integrated IT Ticketing and Log System. This system aims to replace the current manual, email-oriented 
support model with a centralized, web-based platform to improve traceability and efficiency.

2 GENERAL DESCRIPTION 
2.1 Product Context 
Currently, the IT ticketing procedure within the CSIS department relies on inefficient, manual emails, 
leading to a lack of central records, overlooked requests, and poor visibility into ticket statuses and 
technician workloads. The proposed system is a custom-built, web-based application utilizing the 
MERN stack (MongoDB, Express.js, React, Node.js). It functions within the university's secure IT 
ecosystem to consolidate support requests, automate email notifications, and track technician time 
via digital "job cards". 
2.2 User Classes and Characteristics 
Primary Users (IT Staff/Technicians):  
 Characteristics: High technical proficiency. High mobility across multiple floors and academic 
departments. Time-constrained. 
 Needs: Require a mobile-responsive interface for real-time updates on the go. Need digital "job 
cards" with start/stop time tracking to accurately log work duration. Require clear queues of 
prioritized tickets to manage workloads effectively. 
Secondary Users (Students and Staff):  
 Characteristics: Varying levels of technical proficiency. Accustomed to the informal nature of 
sending emails for support. 
 Needs: Require a simple, intuitive interface free of technical jargon. Expect automated transparency 
(knowing exactly what stage their ticket is in). Need automated email confirmations and resolutions. 
Administrators / Management (CSIS IT Supervisors): 
 Characteristics: Focus on operational efficiency, resource allocation, and service delivery metrics. 
 Needs: Require visual dashboards and reporting analytics to track workload trends, average 
turnaround times, and common recurring IT issues.  
2.3 Overview of Functional Requirements 
The system must provide an end-to-end platform for ticket management. Core functionalities include:  
 User & Role Management: Secure login and profile management ensuring users are directed to 
the correct interfaces based on their role (Student/Staff vs. Technician vs. Admin). 
 Structured Ticket Logging: Users can submit detailed IT requests utilizing predefined categories 
(e.g., Hardware, Software, Network) and urgency levels to ensure accurate routing. 
 Unique Traceability: The system automatically generates a unique Ticket ID for every request, 
creating a permanent audit trail. 
 Lifecycle Management: Tickets are systematically tracked through distinct lifecycle states (e.g., 
"New," "Assigned," "In Progress," and "Resolved"). 
 Technician Job Cards: A dedicated dashboard view for IT staff featuring start/stop timer 
functionality to accurately track task duration and manage active workloads. 
 Centralized Communication: Integrated comment-based messaging within each ticket to 
centralize dialogue, completely replacing fragmented email threads. 
 Automated Notifications: The system will automatically trigger and route confirmation, status 
update, and resolution emails to the relevant users. 
 Reporting & Dashboards: Automated aggregation of system data to provide administrators with 
visual metrics on department performance, turnaround times, and technician workloads.

2.4 Overview of Data Requirements 
To support the functional requirements, the system must securely process and store several distinct data 
entities: 
 Ticket Data: Storage of unique Ticket IDs, timestamps (creation, updates, closure), issue descriptions, 
predefined categories, and priority levels. 
 User Information: Collection of student/staff names, NWU email addresses, and assigned system 
roles (User, Technician, Admin) for authentication and notification routing. 
 Operational & Workflow Data: Storage of job card durations (start/stop timestamps), internal 
technician notes, and complete status history logs for auditability. 
 Communication Logs: Sequential storage of user and technician comments linked to specific Ticket 
IDs. 
 Performance Metrics: Aggregated data points used for calculating average response times, resolution 
rates, and workload distribution for management reporting. 
 Compliance: All personal and operational data must be encrypted and handled securely to ensure 
strict compliance with the Protection of Personal Information Act (POPIA) and university data 
governance policies. 
2.5 Operating Environment 
The CSIS IT Ticket Log System is designed as a responsive, cross-platform web application. Because it is 
web-based, it requires no local installation and can be accessed from any internet-enabled device, ensuring 
maximum accessibility for students, staff, and highly mobile IT technicians. 
Target Platforms and Browsers 
 Operating Systems: Fully compatible with Windows (10/11), macOS, and Linux for desktop users. 
Mobile access is supported on Android (8.0+) and iOS (11.3+). 
 Supported Browsers: The system is optimized for modern web browsers, including Google Chrome, 
Mozilla Firefox, Microsoft Edge, and Apple Safari. 
Hardware Requirements

Server & Infrastructure 
 Hosting: The system will be hosted internally on existing CSIS department on-premise servers. 
 Software Stack: Built utilizing the MERN stack. The server environment will require a Node.js runtime 
and a localized MongoDB database instance to ensure data does not leave the university network. 
 Integrations: Requires access to the NWU SMTP relay server to push confirmation and notification 
emails to users automatically

2.6 General Constraints, Assumptions, Dependencies, Guidelines 
 Constraints: Development is restricted to internal student resources to ensure zero licensing costs. The 
solution must adhere strictly to university data security and POPIA policies.  
 Assumptions: It is assumed that all users have consistent access to web browsers and active university

 Dependencies: Successful implementation depends on the availability of internal server space and

2.7 Design and Implementation Constraints 
This section outlines the overarching project boundaries, expectations, and foundational elements guiding 
the development and delivery of the system. 
Constraints 
 Budget Limitations: Development is strictly restricted to internal student resources. The solution must 
utilize open-source frameworks (like React and Node.js) to ensure zero licensing costs. 
 Time Constraints: The system must be developed, tested, and operational by the beginning of the 
second semester to support the 2026 academic cycle. 
 Compliance & Security: The solution must adhere strictly to the Protection of Personal Information 
Act (POPIA) and university data security policies 
Assumptions 
 Access: It is assumed that all target users have consistent access to a web browser, a stable internet 
connection, and an active NWU email account. 
 Digital Literacy: Most users (staff and students) are assumed to possess basic digital literacy and will 
comfortably navigate a standard web form. 
 Infrastructure Stability: It is assumed that the existing NWU email infrastructure is reliable and 
capable of handling the automated system notifications. 
Dependencies 
 Infrastructure Provisioning: Successful implementation is entirely dependent on the timely allocation 
of internal server space and MongoDB database access by the CSIS network administrators. 
 Escalation Workflows: The system's effectiveness relies on coordinating with the main NWU IT 
Department to establish clear technical or procedural hand-offs for escalated tickets. 
 SMTP Access: The notification system depends on the university granting the application permission 
to route emails through its servers. 
Guidelines 
 Development Methodology: The project will follow an Agile/iterative delivery approach using defined 
sprints. This allows for continuous testing and user feedback to manage development risks. 
 User-Centric Design: The interface must prioritize mobile-first design for the technician views, 
acknowledging that IT staff operate across multiple floors and departments. 
 Long-Term Maintainability: Because the developers are students who will eventually graduate, the 
code must be heavily commented, properly version-controlled (e.g., via GitHub), and accompanied by 
comprehensive handover documentation.

2.8 User Documentation 
To support successful adoption, smooth onboarding, and long-term sustainability of the CSIS IT Ticket Log 
System, we will provide comprehensive documentation. The documentation is tailored to the specific 
technical proficiencies of each user class. 
End-User Guides (Students and Staff) 
 Objective: To assist users in transitioning away from the legacy email-based support model to the new 
centralized web portal, minimizing resistance to change. 
 Content: Clear, simple, and highly visual step-by-step instructions. It will cover how to navigate to the 
portal, log a new ticket, categorize an issue, and interpret the automated status emails. 
 Delivery: A brief, downloadable PDF quick-start guide, supplemented by an accessible web-based 
FAQ section directly on the ticketing portal login page. 
Technician and Administrator Manuals 
 Objective: To train IT staff on managing their active workloads and utilizing the system’s advanced 
tracking features. 
 Content: Detailed workflows covering how to filter ticket queues, properly utilize the "Job Card" 
start/stop timers for time tracking, communicate securely within the ticket thread, and generate 
departmental performance analytics. 
Technical Maintenance & Handover Documentation 
 Objective: To guarantee long-term system sustainability. Because the system is developed by 
students who will eventually graduate, seamless knowledge transfer is critical. 
 Content: Comprehensive technical documentation detailing the MERN stack architecture, server 
deployment procedures, MongoDB database schemas, and SMTP email integration protocols. It will 
include troubleshooting guides for common server or database failures. 
Documentation Standardization 
 Formatting: To ensure consistency and academic professionalism, all project-related documentation,

Inputs Technician clicks the "Start Timer" button and subsequently the "Stop Timer" button on the 
ticket interface. 
Processing The system captures the "Start" timestamp. Upon clicking "Stop," it captures the second 
timestamp, calculates the exact duration (in minutes/hours), and sums this with any 
previously logged time on that ticket. It automatically shifts the ticket status to "In Progress". 
Outputs The updated total work duration is saved to the database and visually updated on the ticket 
UI. A time-log audit entry is created. 
 
Centralized Ticket Communication 
Criteria Specification 
Purpose / 
Description 
Consolidate all dialogue regarding a specific issue directly within the ticket to replace 
fragmented email chains. 
Inputs User or Technician types a message into the ticket's comment box and clicks "Send". 
Processing The system validates the text input, appends the sender's ID and current timestamp, and 
pushes the data to the ticket's internal comment array in the database. It triggers a 
notification event. 
Outputs The new message instantly appears in the ticket's chronologically ordered chat thread. An 
email alert is dispatched to the opposing party. 
 
Ticket Lifecycle Management (Resolution) 
Criteria Specification 
Purpose / 
Description 
Provide a structured method for advancing tickets from active states to completion. 
Inputs Technician selects "Resolved" from the status dropdown and inputs a mandatory 
"Resolution Summary" comment. 
Processing The system validates that a resolution summary exists. It updates the ticket state to 
"Resolved," captures the exact closure timestamp, and calculates the total turnaround time 
(Creation Timestamp vs. Closure Timestamp). 
Outputs The ticket is moved from active queues to the archived/resolved queue. An automated email 
is sent to the user notifying them of the resolution.

HTML email template with the dynamic data, and routes it to the NWU SMTP server. 
Outputs An email is successfully dispatched to the target user's NWU inbox containing the update 
and a direct link back to the ticket in the web portal.

3.1 Performance Requirements 
 Response Time: The system must provide near real-time updates for status changes and messaging. 
The UI should respond to standard user inputs (such as submitting a ticket or starting a timer) within 
2.0 seconds under normal network conditions. 
 Availability & Uptime: High availability is required to ensure technicians can log walk-in issues and 
update job cards while on-site. The system targets a 99.9% uptime during standard academic hours.  
 Throughput: The platform must be capable of handling high volumes of concurrent users—specifically 
during peak academic periods—without experiencing data corruption or significant lag. 
 
3.2 Security 
 POPIA Compliance: The system must ensure secure, structured data handling in accordance with the 
Protection of Personal Information Act. Sensitive data must be encrypted in transit using HTTPS/TLS 
protocols.  
 Role-Based Access Control (RBAC): Secure authentication must enforce strict boundaries. Students 
can only access their own requests, technicians can manage their assigned workloads, and admins 
retain global oversight to protect sensitive ticket data.  
 Audit Logging: All critical actions—such as login attempts, status changes, and time entries—must be 
permanently logged with timestamps to ensure complete accountability and traceability. 
 
3.3 Usability 
 Branding & Trust: The interface should be strictly branded to match official university standards, 
fostering immediate user trust and encouraging widespread adoption.  
 Simplicity & Frictionless Adoption: The user guide and portal design must be highly intuitive. By 
keeping the "Submit Ticket" process simple, the system will easily overcome potential user resistance 
to moving away from familiar email habits.  
 Mobile-First Technician View: Because IT staff are highly mobile, all critical technician interfaces (like 
the Job Card timer) must feature touch-friendly targets optimized for smaller mobile screens. 
 Error Prevention: Forms must utilize predefined dropdowns and forced categorical selections to 
prevent invalid data entry and reduce frustration. 
3.4 Other Requirements 
 Scalability: The system architecture must remain modular. While initially designed for CSIS, the 
foundational codebase should allow for potential seamless deployment in other academic departments 
across NWU.  
 Maintenance & Sustainability: To mitigate the risk of knowledge loss when the initial student 
developers graduate, heavily commented code and comprehensive maintenance manuals must be 
provided to ensure new staff can easily take over the application's upkeep.

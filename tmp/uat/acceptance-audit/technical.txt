PROJECT  SCOPE  The  Integrated  IT  Ticketing  and  Log  System  is  a  strategic  initiative  to  digitise,  rationalise  
and

NWU
 
CSIS

The

workload

performance

1.3.1  Objectives  and  Goals 
The  main  objective  of  this  project  is  to  design  a  strong,  web-based  platform  which  could  
provide
 
a
 
single
 
point
 
of
 
entry
 
for
 
all
 
departmental
 
IT
 
requests.
 
Specific
 
objectives
 
include:
 
●  Centralized  Incident  Logging:  Providing  a  single  portal  for  students  and  staff  to  log  
hardware/software
 
faults
 
directly,
 
thus
 
reducing
 
the
 
number
 
of
 
"lost"
 
requests.
 
 ●  Real-Time  Job  Tracking:  Creating  a  technician  dashboard  showing  the  journey  of  a  
ticket
 
from
 
submission
 
to
 
resolution
 
with
 
real-time
 
insights.
 
 ●  Automated  Communication:  Minimizing  the  need  for  manual  follow-ups  by  sending  
email
 
confirmations
 
and
 
status
 
updates
 
automatically.
 
 ●  Data-Driven  Reporting:  Creating  an  audit  trail  of  all  the  resolved  issues  which  
provide
 
management
 
metrics
 
on
 
response
 
times,
 
recurring
 
technical
 
issues
 
and
 
amount
 
of
 
work
 
to
 
each
 
technician.
 
 
1.3.2  Relevant  Benefits  
●  Increased  Productivity:  Reduce  time  spent  for  both  users  and  IT  staff  through  a  
seamless
 
request-and-approval
 
process.
 ●  Enhanced  Transparency:  Users  are  notified  about  their  request  status,  reducing  
uncertainty

 ●  Accountability:  Accurate  tracking  of  resolution  times  and  technician  assignments  
guarantees
 
high

 ●  Strategic  Insights:  It  even  lets  the  department  recognize  high-failure  hardware  or  
essential
 
software

can
 
schedule
 
maintenance
 
beforehand
 
and
 
plan
 
resources
 
accordingly.

SYSTEM  FEATURES  
  
SYSTEM  FEATURE  1:  Centralized  Ticket  Submission  
Portal
 
 
  
DESCRIPTION  AND  PRIORITY  
This  is  a  high  priority  feature  that  will  be  the  gateway  for  all  IT  support  requests.  This  lets  students  and  staff  log  faults  via  a  structured  web  interface  rather  than  informal  verbal  or  email  reporting.  The  feature  allows  technicians  to  capture  specific  data  points  at  the  source  (like  lab  station  numbers  and  urgency  levels)  so  nothing  is  missing  and  they  can  start  repairs  right  away.  
 
STIMULUS  /  RESPONSE  SEQUENCES  
The  user  fills  out  and  submits  the  fault  report  through  the  web  interface  →  The  system  validates  the  input,  creates  a  unique  Ticket  ID  and  makes  an  entry  in  the  MongoDB  database  with  that  id  →  System  then  sends  a  confirmation  notification  to  the  user.  

--- PAGE 14 ---
FUNCTIONAL  REQUIREMENTS  
FR1.1:  Web-based  submission  form:  A  structured  UI  for  users  to  enter  the  fault  categories,  specific  locations  (e.g.,  Lab  G1),  station  IDs  and  detailed  description.  FR1.2:  Priority  assignment  logic:  A  field  that  lets  users  assign  the  importance  of  the  issue  (Low,  Medium,  High),  which  the  system  uses  to  effectively  organize  the  technician  queue.   FR1.3:  Data  persistence  (MongoDB):  The  service  must  persist  the  ticket  document-oriented  format  within  the  collections  of  MongoDB.   
        
SYSTEM  FEATURE  2:  Technician  Job  Card  Dashboard   
  
DESCRIPTION  AND  PRIORITY  
It  is  a  high-priority  feature,  built  primarily  for  CSIS  IT  technicians.  It  offers  a  single  view  of  the  "Job  Card"  where  active  tickets  are  managed  through  their  lifecycle.  It  is  an  important  feature  for  accountability  and  visibility,  as  technicians  can  "claim"  tasks,  update  their  status  from  the  field  in  real-time,  and  formally  escalate  problems  needing  university-wide  IT  support.  
STIMULUS  /  RESPONSE  SEQUENCES  
Technician  selects  a  pending  ticket  from  the  dashboard  and  clicks  on  “Claim”  →  The  system  changes  the  status  to  “In  Progress”,  and  assigns  the  technician  to  the  task  →  Technician  identifies  an  infrastructure  issue  and  selects  “Escalate”  →  The  system  will  ask  you  for  escalation  reason,  change  its  status  to  “Escalated  to  NWU  IT”  ,  and  makes  a  record  for  the  central  IT  gateway  →Technician  fills  out  resolution  notes  and  marks  the  ticket  as  resolved  →  System  the  logs  the  completion  time,  archives  the  ticket,  and  informs  the  user.   
 
FUNCTIONAL  REQUIREMENTS  
FR2.1:  Centralized  management  dashboard:  A  secure  dashboard  that  will  show  you  all  the  open  tickets,  filtered  by  status  (Pending,  In  Progress,  Escalated,  Resolved)  and  sorted  by  priority.   FR2.2:  Status  management  logic:  Backend  component  that  enables  technicians  to  move  a  ticket  through  a  series  of  predefined  states,  ensuring  each  status  change  is  reflected  in  the  audit  log.   FR2.3:  Resolution  logging:  A  required  text-based  input  field  where  technicians  document  the  steps  taken  to  resolve  the  issue  before  closing  the  ticket  officially.   

--- PAGE 15 ---
FR2.4:  Central  IT  Escalation  Trigger:  A  function  used  to  flag  tickets  for  the  NWU  IT  Department  which  creates  a  clear  administrative  record  of  external  hand-offs.  FR2.5:  Workload  &  Performance  Tracking: The  system  shall  automatically  calculate  and  save  the  time  from  a  ticket  is   "Claimed"  to  when  it  is  "Resolved"  for  departmental  reporting.    
        
SYSTEM  FEATURE  3:  Automated  Notification  Engine   
  
DESCRIPTION  AND  PRIORITY  
This  is  a  mid-level  priority  feature,  which  automates  communication  between  the  IT  department  and  the  end  user.  It  eliminates  the  need  for  manual  follow-up  emails,  and  ensures  that  students  and  staff  are  updated  about  the  status  of  their  requests,  which  is  essential  for  visibility  and  trust  within  the  department.   
STIMULUS  /  RESPONSE  SEQUENCES  
Technician  updates  the  ticket  status  in  the  database  →  The  system  sends  an  SMTP  request  through  the  university’s  mail  server  →  The  user  receives  an  automated  email  with  the  latest  status  and  any  comments  from  the  technicians.  
FUNCTIONAL  REQUIREMENTS  
FR3.1:  SMTP  Integration:  A  backend  service  that  connects  to  the  NWU  mail  infrastructure  and  is  responsible  for  sending  automated,  template  based  emails.   FR3.2:  Trigger-based  alerts:  Logic  that  automatically  triggers  notification  events  whenever  a  ticket  is  created,  claimed,  or  resolved.   FR3.3:  Automated  ticket  receipt:  The  system  should  auto-generate  and  email  a  summary  of  the  filed  ticket  (with  the  unique  ID)  immediately  after  submission  is  deemed  successful.    
  
 
SYSTEM  FEATURE  4:  Audit  Logging  and  Reporting   
  

--- PAGE 16 ---
DESCRIPTION  AND  PRIORITY  
This  feature  is  of  low-to-medium  priority,  targeted  towards  departmental  administrators.  It  offers  a  non-modifiable  record  of  all  functions  carried  out  on  your  system,  which  is  essential  for  digging  into  trends  in  technical  problems  and  tracking  overall  IT  support  performance.  
 
STIMULUS  /  RESPONSE  SEQUENCES  
An  administrator  asks  for  a  performance  report  for  a  specific  period  →  The  system  extracts  historical  ticket  data  and  calculates  important  metrics,  like  average  resolution  time  →  The  system  generates  a  summary  page  or  exportable  file  for  the  management  review.  
FUNCTIONAL  REQUIREMENTS  
FR4.1:  Immutable  audit  logs:  A  background  service  that  keeps  a  record  of  the  ticket  modifications  such  as  who  made  the  modification  and  at  what  time.   FR4.2:  Historical  data  filtering:  A  UI  where  admins  can  filter  through  past  tickets  by  attributes  such  as  date,  technician,  or  hardware  category.   FR4.3:  Performance  metric  calculation:  Backend  logic  to  calculate  "Time-to-Resolution"  of  completed  tickets  that  helps  identify  trends  for  laboratory  maintenance     
 
 
  
SYSTEM  FEATURE  5:  TWO-WAY  COMMUNICATION  
STREAM
 
 
  
DESCRIPTION  AND  PRIORITY  
This  is  a  high  priority  feature  which  will  allow  the  ticket  reporters  to  reach  out  directly  to  the  assigned  technician.  This  allows  for  technical  follow-up  questions  to  be  answered  from  within  the  platform,  provides  all  troubleshooting  notes  in  a  single  repository  and  replaces  informal  email-based  conversations  with  an  auditable  history.  
STIMULUS  /  RESPONSE  SEQUENCES  
The  technician  notices  a  lack  of  detail  and  writes  a  comment  to  the  ticket  →  System  saves  the  comment  and  triggers  the  Notification  Engine  to  inform  the  user  →  User  clicks  on  the  ticket  link  and  write  a  response  →  System  updates  communication  stream,  notifies  assigned  technician,  and  keeps  track  of  the  chronological  log  for  audit  purpose.  
FUNCTIONAL  REQUIREMENTS  
FR  5.1:  Threaded  Commenting:  System  should  allow  a  comment  thread  chronologically  ordered  to  be  attached  per  unique  Ticket  ID.  This  comment  thread  is  visible  by  both  the  reporter  (who  created  the  ticket)  and  technician  once  they  are  assigned  to  that  ticket.   

--- PAGE 17 ---
FR  5.2:  Real-time  Notification  Trigger:  The  system  must  send  a  real-time  notification  (using  the  SMTP  gateway)  to  the  counter-party  each  time  a  new  comment  is  added  to  the  stream  to  ensure  prompt  response  times.  FR  5.3:  Internal  Technician  Notes:  The  system  will  allow  techs  to  post  "Internal  Only"  comments  that  are  read  by  IT  staff  but  not  viewable  to  the  student/staff  reporter.  FR  5.4:  Audit  Persistence:  Once  posted,  all  communication  in  the  stream  must  be  immutable  (no  deletion),  to  preserve  complete  transparency  on  the  results  of  the  troubleshooting  process.   FR  5.5:  File  Attachments  (Future  Enhancement):  The  communication  architecture  shall  be  designed  with  the  potential  to  upload  screenshots  or  log  files,  as  specified  in  the  System  Specification.
